# Which real deployments give a reconnecting client a peer that accepts then closes?

Research for [Which real deployments give a reconnecting client a peer that accepts then closes?](https://github.com/org-utils/ioredis-toolkit/issues/109), part of [Map: this package's position on Bun](https://github.com/org-utils/ioredis-toolkit/issues/102).

Researched 2026-10-15. Reading only: source code, vendor docs and issue trackers. No Docker, Redis or Bun runs.

## Why the peer's behaviour matters

Under Bun before 1.4 (seen on 1.3.10), ioredis 5.11.1 can hang for good when its socket reaches `'connect'`, writes its handshake commands, and the peer then closes without serving. Bun never fails the parked writes, so `'close'` never comes ([Why does ioredis wait forever after connect under Bun?](https://github.com/org-utils/ioredis-toolkit/issues/103)). A refused connection never reaches `'connect'` and is handled ([Does the Bun reconnect hang reproduce outside Docker Desktop?](https://github.com/org-utils/ioredis-toolkit/issues/105)). Bun 1.4.3 recovers ([Does the Bun reconnect hang still happen on Bun 1.4.x?](https://github.com/org-utils/ioredis-toolkit/issues/108)).

The peers below fall into five shapes:

| Shape | What the client sees | Bun < 1.4 |
| --- | --- | --- |
| **Refuses** | RST or ICMP unreachable in reply to the SYN: `ECONNREFUSED` | handled |
| **Times out** | SYN unanswered: ioredis `connectTimeout` fires | handled |
| **Accepts, then closes at once** | handshake completes, then FIN/RST within milliseconds, without the peer serving anything | **the reproduced trigger** (local dropper, Docker Desktop's proxy) |
| **Accepts, then closes later** | handshake completes, the peer reads the client's first bytes or holds the connection for a while, then closes | **not tested**; see the caveat below |
| **Stays open** | the peer answers commands with errors (`-NOAUTH`, `-LOADING`, a proxy's `-ERR`) | handled; not a close |

**Caveat: the peer is necessary but not sufficient.** [Do Cluster failover and standalone restarts hang the same way under Bun?](https://github.com/org-utils/ioredis-toolkit/issues/106) found that standalone and Cluster *reconnects* recover under Bun 1.3.10 even behind Docker Desktop's accept-then-close proxy. Only a Sentinel reconnect and a standalone *first* connect reached the stuck write ([Does the Bun reconnect hang still happen on Bun 1.4.x?](https://github.com/org-utils/ioredis-toolkit/issues/108)). Why wasn't investigated. So a row below that says "accepts then closes" means exposure on those two paths, not on every reconnect.

### Verdict

Accept-then-close is not exotic. Every **user-space TCP proxy** in front of Redis produces it while its backend is down: HAProxy, Envoy, an Istio sidecar mesh, `docker-proxy` on host loopback, `kubectl port-forward`. **Redis itself** produces it at `maxclients` and in protected mode. Plain networks do not: a dead Redis on a live host refuses, a dead host times out, kube-proxy rejects Services with no endpoints in every mode, and the cloud L4 pass-through balancers (AWS NLB TCP, GCP passthrough, Azure LB) hand the client the backend's own answer or nothing. The managed failover endpoints are undocumented on this point.

So a Bun < 1.4 user is exposed in practice when their client reaches Redis through a proxy or a mesh, or Redis is at `maxclients`, and the client is on one of the paths that reach the stuck write (Sentinel reconnect, first connect). The sharpest real case is an app starting while Redis is down in an Istio mesh, or a Sentinel client in such a mesh during a failover. HAProxy's own documented Redis setup also fits: it checks for `role:master`, so during a failover no server is UP.

## Findings in detail

### Redis itself

- **`maxclients` reached: accepts, writes an error, closes at once.** `acceptCommonHandler` checks the client count right after `accept()`. Over the limit it writes `-ERR max number of clients reached\r\n` (Cluster: `… + cluster connections reached`) as a best-effort write and calls `connClose`. The source comment says that on a TLS port "no handshake was done yet so nothing is written and the connection will just drop" ([networking.c L1764–L1787](https://github.com/redis/redis/blob/4e4c65bc71dd63c1d2dbe999b3d3d86d49772cc5/src/networking.c#L1764-L1787)). This is the dropper shape from the root-cause ticket plus one line of data, so it is the closest Redis-native match. It was not run under Bun. Sentinel runs the same networking code, so it applies to Sentinel processes too.
- **Protected mode: accepts, writes `-DENIED`, closes at once.** With `protected-mode yes` and a default user with no password, `clientAcceptHandler` writes the long `-DENIED Redis is running in protected mode …` message to any non-loopback client and frees it ([networking.c L1686–L1721](https://github.com/redis/redis/blob/4e4c65bc71dd63c1d2dbe999b3d3d86d49772cc5/src/networking.c#L1686-L1721)). This is a persistent misconfiguration, not a failover window: under Node it shows as an error loop, under Bun < 1.4 it may show as a hang.
- **Plain TCP to a `tls-port`: accepts, closes later.** The accept path runs `SSL_accept`. When the client's first bytes are RESP and not a ClientHello, the handshake fails, the connection goes to `CONN_STATE_ERROR`, and `clientAcceptHandler` frees it ([tls.c L804–L822](https://github.com/redis/redis/blob/4e4c65bc71dd63c1d2dbe999b3d3d86d49772cc5/src/tls.c#L804-L822), [networking.c L1675–L1684](https://github.com/redis/redis/blob/4e4c65bc71dd63c1d2dbe999b3d3d86d49772cc5/src/networking.c#L1675-L1684)). The close comes after Redis has read the client's first write, which is a different timing from the reproduced trigger. Also a persistent misconfiguration.
- **ACL and `AUTH` failures: the connection stays open.** A failed `AUTH` returns an error and the client "needs to try a new password", and Redis denies other commands until the connection authenticates ([AUTH](https://redis.io/docs/latest/commands/auth/)). Nothing in the accept path closes for authentication. ioredis may itself give up (`recoverFromFatalError`), but that is the client closing, not the peer.
- **Shutdown.** `prepareForShutdown` with replicas lagging and `shutdown-timeout` non-zero pauses client writes and returns, leaving the listener open ([server.c L5214–L5226](https://github.com/redis/redis/blob/4e4c65bc71dd63c1d2dbe999b3d3d86d49772cc5/src/server.c#L5214-L5226)): new clients connect and are served, and their connections close normally when the process exits. `finishShutdown` saves the dataset (if configured) and only then closes the listening sockets ([server.c L5426–L5427](https://github.com/redis/redis/blob/4e4c65bc71dd63c1d2dbe999b3d3d86d49772cc5/src/server.c#L5426-L5427)). During that save the event loop is blocked but the kernel still completes handshakes into the accept backlog, so a reconnecting client gets `'connect'` and writes. When the listener closes, Linux removes every queued child and `tcp_disconnect` sends an active RST for `ESTABLISHED` sockets ([inet_csk_listen_stop](https://github.com/torvalds/linux/blob/0fcb05b72344f40806cbe810de8872f1698bf053/net/ipv4/inet_connection_sock.c#L1466-L1480), [inet_child_forget](https://github.com/torvalds/linux/blob/0fcb05b72344f40806cbe810de8872f1698bf053/net/ipv4/inet_connection_sock.c#L1369-L1372), [tcp_need_reset / tcp_disconnect](https://github.com/torvalds/linux/blob/0fcb05b72344f40806cbe810de8872f1698bf053/net/ipv4/tcp.c#L3322-L3380)). The same applies to any Redis that is blocked and then killed. The window lasts as long as the save or the block, and the RST arrives after the client's writes have reached the kernel, so it is a "closes later" peer. Once the process is gone the port refuses.

### TCP proxies and load balancers

- **HAProxy.** A frontend accepts the client connection before a server is chosen. In `back_handle_st_req`, when `srv_redispatch_connect` gets no server (`SRV_STATUS_NOSRV`, logged as `<NOSRV>`), the stream is aborted, shut down and closed at once ([backend.c L2694–L2712](https://github.com/haproxy/haproxy/blob/aedad8b8616a3092143e19ad4728a81fcadbc0c4/src/backend.c#L2694-L2712), [L2396–L2404](https://github.com/haproxy/haproxy/blob/aedad8b8616a3092143e19ad4728a81fcadbc0c4/src/backend.c#L2396-L2404)). When a server is UP but refuses, HAProxy retries (`retries`, default 3) with a turn-around timer of `min(timeout connect, 1s)` before closing ([configuration.txt L12869–L12891](https://github.com/haproxy/haproxy/blob/aedad8b8616a3092143e19ad4728a81fcadbc0c4/doc/configuration.txt#L12869-L12891), [defaults.h L291](https://github.com/haproxy/haproxy/blob/aedad8b8616a3092143e19ad4728a81fcadbc0c4/include/haproxy/defaults.h#L291)). The manual's own `tcp-check` example for Redis marks only the server that reports `role:master` as UP ([configuration.txt L12416–L12428](https://github.com/haproxy/haproxy/blob/aedad8b8616a3092143e19ad4728a81fcadbc0c4/doc/configuration.txt#L12416-L12428)). During a failover that leaves zero servers UP until the new master passes its checks, so every connection in that window is accepted and closed.
- **Envoy `tcp_proxy`.** The downstream connection is already accepted when the filter's `onNewConnection` runs. Reads are disabled until an upstream connects ([tcp_proxy.cc L512–L517](https://github.com/envoyproxy/envoy/blob/3070ce89c5e8e1602534642de213bab3e1ef889a/source/common/tcp_proxy/tcp_proxy.cc#L512-L517)), so the client's writes sit unread. With no healthy host it sets `NoHealthyUpstream` and closes the downstream with `NoFlush` at once ([L813–L817](https://github.com/envoyproxy/envoy/blob/3070ce89c5e8e1602534642de213bab3e1ef889a/source/common/tcp_proxy/tcp_proxy.cc#L813-L817), [L532–L547](https://github.com/envoyproxy/envoy/blob/3070ce89c5e8e1602534642de213bab3e1ef889a/source/common/tcp_proxy/tcp_proxy.cc#L532-L547)). When the upstream connect fails it retries up to `max_connect_attempts` (default 1, [L237](https://github.com/envoyproxy/envoy/blob/3070ce89c5e8e1602534642de213bab3e1ef889a/source/common/tcp_proxy/tcp_proxy.cc#L237)) and then closes the same way ([L1400–L1406](https://github.com/envoyproxy/envoy/blob/3070ce89c5e8e1602534642de213bab3e1ef889a/source/common/tcp_proxy/tcp_proxy.cc#L1400-L1406), [L1424–L1435](https://github.com/envoyproxy/envoy/blob/3070ce89c5e8e1602534642de213bab3e1ef889a/source/common/tcp_proxy/tcp_proxy.cc#L1424-L1435)).
- **Envoy `redis_proxy`** is protocol-aware and keeps the connection: with no upstream it answers each command with a `no upstream host` error ([command_splitter_impl.cc L274](https://github.com/envoyproxy/envoy/blob/3070ce89c5e8e1602534642de213bab3e1ef889a/source/extensions/filters/network/redis_proxy/command_splitter_impl.cc#L274)).
- **Istio sidecar mode.** `istio-iptables` redirects all outbound TCP from the pod to Envoy's outbound port ([run.go L266](https://github.com/istio/istio/blob/4e2c1c576e33a7b411ee7f38ac4bb9dd45c36631/tools/istio-iptables/pkg/capture/run.go#L266)). The application's `connect()` therefore always completes against the local sidecar, and Envoy's `tcp_proxy` closes it if the upstream has no healthy host or refuses (above). Inbound capture works the same way on the server pod, so a Redis pod whose process is down but whose sidecar is up also accepts and closes. This is inferred from the two sources; Istio's docs do not describe it. Ports excluded from capture behave like a plain network.
- **Istio ambient (ztunnel).** An open issue reports, with packet captures on AKS and Istio 1.26, that "ztunnel accepts the connection immediately, before any upstream/HBONE leg exists" and resets it later, and that sidecar mode shows the same class through `no healthy host` ([istio/istio#60955](https://github.com/istio/istio/issues/60955)). That is a user report with no maintainer confirmation yet, so it is unconfirmed here.
- **Kubernetes Services with zero endpoints: refuse in every kube-proxy mode.** iptables mode installs a `REJECT` rule commented `"<svc> has no endpoints"` ([proxier.go L889–L896](https://github.com/kubernetes/kubernetes/blob/d4f9e04d5d2a7f43314dd93ca2efcf13ad17c46f/pkg/proxy/iptables/proxier.go#L889-L896)). nftables mode sends them to a `reject` chain through the `no-endpoint-services` map ([proxier.go L620–L635](https://github.com/kubernetes/kubernetes/blob/d4f9e04d5d2a7f43314dd93ca2efcf13ad17c46f/pkg/proxy/nftables/proxier.go#L620-L635)). In IPVS mode a virtual service with no real server falls to the kernel's `ip_vs_leave`, which sends ICMP port unreachable ([ip_vs_core.c L762–L845](https://github.com/torvalds/linux/blob/0fcb05b72344f40806cbe810de8872f1698bf053/net/netfilter/ipvs/ip_vs_core.c#L762-L845)); kube-proxy also rejects new connections to IPVS-bound addresses that match no service ([ipvs proxier.go L1451–L1454](https://github.com/kubernetes/kubernetes/blob/d4f9e04d5d2a7f43314dd93ca2efcf13ad17c46f/pkg/proxy/ipvs/proxier.go#L1451-L1454)). A Service whose endpoint pod is alive but not listening also refuses, from the pod's kernel, unless a sidecar is in the way.
- **`kubectl port-forward`.** The local listener accepts, and `handleConnection` closes the local connection (`defer conn.Close()`) once the forward to the pod fails ([portforward.go L460–L461](https://github.com/kubernetes/client-go/blob/f37dc9914211f23991536015795949b0ddcb26c3/tools/portforward/portforward.go#L460-L461)). The close comes after a round trip to the API server, so it is a "closes later" peer. A development setup, like Docker.
- **AWS NLB.** The docs describe TLS termination as what "also terminates a TCP connection" and opens a separate one to the target, which implies a TCP listener does not proxy. When all targets fail health checks, or the target group is empty, the NLB fails open and sends traffic to all targets ([NLB health checks](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/target-group-health-checks.html)). So with a TCP listener the client gets the target's own answer. The TLS listener case is unconfirmed.
- **GCP.** Passthrough Network Load Balancers "are not proxies" and backend responses go straight to the client ([docs](https://docs.cloud.google.com/load-balancing/docs/network/networklb-backend-service)). Proxy Network Load Balancers terminate the client's TCP at the load balancer, and "if all backends are unhealthy, the load balancer drops traffic" ([docs](https://docs.cloud.google.com/load-balancing/docs/tcp)). Whether that means accept-then-close or no handshake is not stated: unconfirmed.
- **Azure Load Balancer** is pass-through. With all probes down, "No new flows are sent to the backend pool" ([health probes](https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-custom-probe-overview)), so the client's SYN goes unanswered (inferred: times out).
- **Twemproxy** keeps the client connection when a backend is down and answers the request with `-ERR <strerror>` ([nc_request.c L518–L544](https://github.com/twitter/twemproxy/blob/60aaf855ba2e15e20d0efbe440c8ff071b719580/src/nc_request.c#L518-L544), [nc_message.c](https://github.com/twitter/twemproxy/blob/60aaf855ba2e15e20d0efbe440c8ff071b719580/src/nc_message.c)). Aside: it closes the client on any command it does not support ([nc_redis.c L1323–L1326](https://github.com/twitter/twemproxy/blob/60aaf855ba2e15e20d0efbe440c8ff071b719580/src/proto/nc_redis.c#L1323-L1326), [nc_message.c L657–L660](https://github.com/twitter/twemproxy/blob/60aaf855ba2e15e20d0efbe440c8ff071b719580/src/nc_message.c#L657-L660)), and it has no `CLIENT` or `INFO`. So ioredis's default `CLIENT SETINFO` gets every connection closed after the first command, on any runtime. That is a separate incompatibility, not a failover window. Predixy and other Cluster proxies were not checked.

### Managed Redis failover endpoints

None of the four vendors documents what a *new* connection gets during a failover, so all four are unconfirmed.

- **AWS ElastiCache:** on failover the failed primary "is taken offline" and ElastiCache "propagates the DNS name of the promoted replica" to the primary endpoint. Engines 4.0.10 and earlier may see "a brief write interruption associated with DNS updates" ([Multi-AZ](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/AutoFailover.html)). What a client with stale DNS gets from the old node is not documented. ElastiCache Serverless sits behind a proxy layer whose behaviour was not checked.
- **Azure Cache for Redis:** every node sits behind "a shared load balancer with a single virtual IP address", and on failover "the old primary node closes existing connections" ([Failover and patching](https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-failover)). Nothing is said about new connections during the swap.
- **Google Memorystore:** the endpoint keeps the same IP, "Memorystore for Redis drops all connections to the primary endpoint", and the instance is unavailable for about 15–30 s ([high availability](https://docs.cloud.google.com/memorystore/docs/redis/high-availability-for-memorystore-for-redis)). Whether new connections are refused, accepted or reset is not stated.
- **Redis Cloud / Redis Software:** clients connect to a proxy that hides shard failover; "the cluster attempts to prevent any existing client connections from being disconnected" ([proxy policy](https://redis.io/docs/latest/operate/rs/databases/configure/proxy-policy/)). Its behaviour while it has no shard to route to, or while it restarts, is not documented.

### Docker port publishing

- **Linux, default `userland-proxy: true`.** `docker-proxy` accepts the client, dials the container, and on a dial error closes the client at once ([tcp_proxy_linux.go L27–L32](https://github.com/moby/moby/blob/0351b2428f7ebb306dd0c229891d394cc29782b0/cmd/docker-proxy/tcp_proxy_linux.go#L27-L32)). It only sees traffic the NAT rules leave to it. The bridge driver sets `Hairpin: !config.EnableProxy` ([bridge_linux.go L200](https://github.com/moby/moby/blob/0351b2428f7ebb306dd0c229891d394cc29782b0/daemon/libnetwork/drivers/bridge/bridge_linux.go#L200)), and without hairpin the `nat OUTPUT` jump excludes `127.0.0.0/8` ([network.go L201–L208](https://github.com/moby/moby/blob/0351b2428f7ebb306dd0c229891d394cc29782b0/daemon/libnetwork/drivers/bridge/internal/iptabler/network.go#L201-L208)). So:
  - a client on the host using `127.0.0.1:<port>` goes through `docker-proxy`: **accepts, then closes** when nothing listens in the container;
  - a client on another host, or on the host using a non-loopback address, is DNATed to the container: **refuses** (the container's kernel resets).
- **Linux, `userland-proxy: false`.** Hairpin DNAT covers loopback too and no proxy runs, so every client is **refused**.
- **Container stopped.** `Leave` calls `releasePorts`, which "frees their host-port reservations, rules and proxies" ([bridge_linux.go L1525–L1530](https://github.com/moby/moby/blob/0351b2428f7ebb306dd0c229891d394cc29782b0/daemon/libnetwork/drivers/bridge/bridge_linux.go#L1525-L1530)), so the host port **refuses**. The port stays published only while the container that owns it runs. In this repo's `docker/sentinel.compose.yml` the ports belong to the `net` container, which keeps running when `redis-master` dies, so on Linux a host client on `127.0.0.1` would get the same accept-then-close as on Docker Desktop (inferred from the source above, not run).
- **Docker Desktop for macOS** accepted and closed in [Under Bun, an ioredis Sentinel client never recovers from a failover](https://github.com/org-utils/ioredis-toolkit/issues/101). Its host-side forwarding is not documented at this level. The Docker docs pages on port publishing and packet filtering do not describe which traffic `docker-proxy` handles either; the answer above comes from the moby source.

## Unconfirmed

- AWS ElastiCache, Azure Cache for Redis, Google Memorystore and Redis Cloud / Redis Software failover endpoints: no primary source says what a new connection gets mid-failover.
- AWS NLB TLS listeners and GCP proxy Network Load Balancers with no healthy backend: they terminate TCP, but the docs do not say whether the handshake completes before they drop the client.
- Istio ambient (ztunnel): reporter-measured only ([istio/istio#60955](https://github.com/istio/istio/issues/60955)).
- Istio sidecar behaviour is inferred from Istio's iptables source and Envoy's `tcp_proxy` source, not from an Istio doc.
- Whether the "closes later" peers (TLS-port mismatch, Redis blocked then exiting, HAProxy retrying, `kubectl port-forward`) trigger the Bun < 1.4 hang. Only "closes at once" peers have been reproduced (local dropper, Docker Desktop). A run with a server that reads the client's first bytes, or waits 100 ms to 1 s, before closing would settle it.
- `maxclients` and protected mode match the dropper shape but add one line of data before closing; they were not run under Bun.
